Use-After-Free (UAF) é usar um ponteiro depois de a memória ter sido liberada. O `free` devolve o chunk ao alocador, mas **não altera a variável que guarda o ponteiro**: ela continua apontando para o mesmo endereço (*dangling pointer*).

```c
char *ptr = malloc(100);
free(ptr);
strcpy(ptr, "data");      // UAF: ptr ainda aponta para o chunk liberado
```

A correção é `ptr = NULL` depois do `free`, e é isso que os programas vulneráveis esquecem. O cenário típico em CTF é o desafio de "notas" (criar, editar, ver, apagar) em que o `delete` chama `free(notes[i])` sem zerar `notes[i]`, e `view`/`edit` continuam aceitando o índice.

## O que o ponteiro enxerga

Depois do `free`, a memória apontada pode estar em dois estados, e cada um dá um tipo de ataque:

### 1. Metadados do alocador

Enquanto o chunk está livre, os primeiros bytes dos dados são `fd`, `bk` e, no tcache, a `key`.

| Primitiva | Efeito | Detalhes |
|---|---|---|
| **Leitura** (view após delete) | Vaza `fd`: endereço da **heap** (tcache/fastbin) ou da **libc** (unsorted bin) | [Safe Linking](./safe-linking.mdx), [Leak de libc](./malloc-consolidate.mdx) |
| **Escrita** (edit após delete) | Sobrescreve `fd`: o `malloc` passa a devolver um endereço arbitrário | [Tcache Poisoning](./tcache.mdx#tcache-poisoning) |
| **Escrita** na `key` | Desarma a detecção de double free do tcache | [Tcache keys](./tcache.mdx#tcache-keys-glibc-229) |
| **`free` de novo** (delete após delete) | [Double Free](./double-free.mdx) | |

### 2. Confusão entre objetos

O alocador devolve o chunk liberado na próxima alocação de tamanho compatível. Se o programa aloca ali um objeto de **outro tipo**, os dois ponteiros (o pendurado e o novo) enxergam a mesma memória com interpretações diferentes:

```c
struct Handler { void (*func)(); char name[24]; };   // 0x20 bytes

struct Handler *h = malloc(sizeof(struct Handler));
h->func = original;
free(h);                          // h continua apontando para o chunk

char *nota = malloc(0x20);        // mesmo tamanho: recebe o MESMO chunk
read(0, nota, 0x20);              // escrevemos os 8 primeiros bytes

h->func();                        // executa o endereço que escrevemos
```

Funciona nos dois sentidos: escrever pelo objeto novo e usar pelo antigo (como acima), ou ler pelo ponteiro antigo dados que o objeto novo guardou (ponteiros, segredos).

Alvos comuns dentro do objeto: ponteiros de função, ponteiros para buffers (viram leitura/escrita arbitrária quando o programa os usa), campos de tamanho e, em C++, o ponteiro da vtable no início do objeto.

Para o objeto novo cair no chunk certo:

- Peça um tamanho que gere **o mesmo tamanho de chunk** do objeto liberado (veja a [tabela de conversão](./index.mdx#o-campo-size)).
- Tcache e fastbin são LIFO: o último chunk liberado é o primeiro devolvido.
- `calloc` zera a memória e, em glibc mais antigas, não tira chunks do tcache.

## Identificando

- No decompilador: um `free(x)` sem `x = NULL` em seguida, ou uma cópia do ponteiro que sobrevive ao `free` (outra struct, outra variável global).
- Dinamicamente: apague um item e tente vê-lo ou editá-lo. No pwndbg, confira com `bins` se o chunk está na lista e com `x/4gx` o que há nele.
