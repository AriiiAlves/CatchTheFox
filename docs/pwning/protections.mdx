As mitigações ativas em um binário definem quais ataques são viáveis. A primeira coisa a fazer com qualquer desafio é rodar o `checksec`.

## Verificando as proteções de um arquivo

O `checksec` vem com o pwntools (`pip install pwntools`) ou como pacote separado (`sudo apt install checksec`):

```bash
pwn checksec ./arquivo       # pwntools
checksec --file=./arquivo    # pacote do apt
```

<div style={{textAlign: 'center'}}>
    ![Saída do checksec](/docs-img/bin-protections.png)
</div>

- **Arch**: arquitetura, tamanho da palavra e [endianness](../introduction/endianness.mdx). `i386-32-little` é x86 de 32 bits; `amd64-64-little` é x86-64.
- **Stripped**: se os símbolos foram removidos (veja [Debugging com GDB](../introduction/gdb.md#compilando-sem--g--stripped)).

## Resumo

| Proteção | O que impede | Como contornar |
|---|---|---|
| **RELRO** (Full) | Escrita na GOT | Escolher outro alvo: return address, hooks, `FILE`, `exit` handlers |
| **Canary** | Overflow linear até o return address | Vazar o canary; escrita não linear (índice, format string); brute force em `fork` |
| **NX** | Executar código na stack/heap | ROP, ret2libc; `mprotect` e depois shellcode |
| **PIE** | Usar endereços fixos do binário | Vazar um endereço do binário; partial overwrite |
| **ASLR** | Usar endereços fixos de libc, stack e heap | Vazar um endereço da região; partial overwrite |
| **Fortify** | Alguns overflows e `%n` | Depende do caso; muitas funções não são cobertas |
| **CET** (IBT + Shadow Stack) | JOP/COP e ROP | Em geral não é aplicado em user space nos CTFs |

## RELRO (Relocation Read-Only)

Controla se as tabelas preenchidas pelo dynamic linker ficam graváveis depois da inicialização: a GOT, `.init_array`, `.fini_array` e `.dynamic`. (A PLT é código e já é somente leitura.)

| Modo | Resolução de símbolos | GOT |
|---|---|---|
| **No RELRO** | Lazy binding | Gravável, assim como `.fini_array` e `.dynamic` |
| **Partial RELRO** | Lazy binding (na primeira chamada de cada função) | `.got.plt` **gravável** durante toda a execução |
| **Full RELRO** | Tudo resolvido na inicialização (`BIND_NOW`) | Somente leitura |

Com Partial RELRO (o padrão do gcc em muitas distribuições), [GOT Overwrite](./stack/got-overwrite.md) funciona. Com Full RELRO, a escrita arbitrária precisa de outro alvo. Note que o RELRO é por binário: a libc tem a própria GOT, que até a glibc 2.38 era Partial RELRO e continuava sendo um alvo válido.

## Stack Canary/SSP (Stack-Smashing Protector)

O compilador coloca um valor aleatório entre as variáveis locais e o `rbp` salvo, e confere esse valor antes do `ret`. Um overflow linear que chegue ao return address passa por cima do canary, a verificação falha e o programa aborta em `__stack_chk_fail` (`*** stack smashing detected ***`).

No assembly, é fácil de reconhecer:

```nasm
mov    rax, QWORD PTR fs:0x28      ; prólogo: lê o canary da TLS
mov    QWORD PTR [rbp-0x8], rax
...
mov    rcx, QWORD PTR [rbp-0x8]    ; epílogo: compara
xor    rcx, QWORD PTR fs:0x28
je     fim
call   __stack_chk_fail
```

Propriedades úteis:

- O valor de referência fica na TLS (`fs:0x28` em x86-64, `gs:0x14` em x86) e é o **mesmo para todas as funções** do processo. Vazou uma vez, vale para todas.
- O byte menos significativo é sempre `0x00`, para que funções de string não o imprimam por acidente. Consequência: se você sobrescrever **só esse byte** com um overflow, um `puts`/`printf("%s")` do buffer imprime os outros 7 bytes do canary.
- Processos criados com `fork()` herdam o canary do pai.

**Contorno**

- **Vazar e reescrever**: obtenha o canary ([Format Strings](./stack/format-strings.md), leitura fora dos limites, o truque do byte nulo acima) e coloque o valor correto no payload, na posição dele.
- **Pular por cima**: escritas não lineares, como [Array Indexing](./others/array-indexing.md) ou `%n`, alcançam o return address sem tocar no canary.
- **Brute force**: em servidores que fazem `fork()` por conexão, descubra o canary byte a byte (no máximo 256 tentativas por byte): o byte certo é o que não derruba o processo filho.
- **Não precisar dele**: o canary não protege variáveis locais entre o buffer e ele ([BOF de variáveis](./stack/buffer-overflow/variables.md)), nem a heap.

## NX (No-Execute) ou DEP (Data Execution Prevention)

Páginas de dados (stack, heap, `.data`, `.bss`) são mapeadas sem permissão de execução. O processador se recusa a executar instruções nelas, o que mata a injeção de [shellcode](./stack/buffer-overflow/shellcode.md).

**Contorno**: reutilizar código que já é executável, com [ROP](./stack/rop/index.mdx) e [ret2libc](./stack/rop/ret2libc.mdx). Também dá para usar um ROP curto que chama `mprotect` (ou `mmap`) para criar uma região executável e, só então, pular para o shellcode.

Confira as permissões reais com `vmmap` no pwndbg/GEF. Um binário com `NX disabled` ou `Stack: Executable` é um convite para shellcode.

## PIE (Position-Independent Executable) + ASLR (Address Space Layout Randomization)

São duas coisas diferentes que se complementam:

- **ASLR** é do kernel: randomiza a base da stack, da heap e das bibliotecas (libc) a cada execução.
- **PIE** é do binário (`-pie` / `-no-pie`): permite que o próprio executável seja carregado em uma base aleatória.

| | Binário (`.text`, GOT, `.bss`) | libc, stack, heap |
|---|---|---|
| Sem PIE, com ASLR | **Fixo** (`0x400000` em x86-64) | Aleatório |
| PIE, com ASLR | Aleatório (`0x55...` / `0x56...`) | Aleatório |
| ASLR desligado | Fixo | Fixo |

Sem PIE, endereços de funções, gadgets e GOT do binário podem ser usados direto, mesmo com ASLR.

**Contorno**

A randomização muda só a **base** de cada região. Os offsets internos são constantes, então **um único endereço vazado de uma região revela a região inteira**: `base = leak - offset_do_que_vazou`. Regiões diferentes têm bases independentes (um leak do binário não revela a libc). A exceção é o que é mapeado por `mmap`: libc, `ld.so` e chunks grandes costumam ficar a distâncias constantes entre si.

- **Leak**: [Format Strings](./stack/format-strings.md), [Array Indexing](./others/array-indexing.md), strings sem terminador, `puts(puts@got)` via ROP, chunks livres na heap.
- **[Partial Overwrite](./stack/rop/partial-overwrite.mdx)**: os 12 bits baixos de um endereço não são randomizados.
- **Brute force**: viável em 32 bits (poucos bits de entropia), raramente em 64.

As bases são sempre alinhadas em página, então terminam em `000`. Se a base que você calculou não termina assim, o offset está errado.

## Fortify Source

Com `-D_FORTIFY_SOURCE=2` (ou `3`) e otimização ligada, o compilador troca funções como `strcpy`, `memcpy`, `read` e `printf` por versões `__*_chk`, que recebem o tamanho do buffer de destino quando o compilador consegue determiná-lo e abortam se ele for excedido.

Efeitos relevantes:

- Overflows simples em buffers de tamanho conhecido passam a abortar (`*** buffer overflow detected ***`).
- Em [Format Strings](./stack/format-strings.md), o `__printf_chk` recusa `%n` quando a format string está em memória gravável, e recusa acessos posicionais (`%7$p`) que pulem argumentos. Leaks com `%p` em sequência continuam funcionando.

## IBT (Indirect Branch Tracking)

O IBT faz parte do Intel CET (Control-flow Enforcement Technology), junto com o Shadow Stack:

- **IBT**: todo `jmp`/`call` **indireto** precisa cair em uma instrução `endbr64` (`endbr32` em 32 bits). Protege contra JOP/COP. Não verifica `ret`.
- **Shadow Stack**: mantém uma cópia protegida dos endereços de retorno e compara a cada `ret`. É o que protege contra ROP.

Na prática, o Linux ainda não aplica IBT em user space, e o Shadow Stack depende de kernel, glibc e hardware recentes e precisa ser habilitado. Nos CTFs, o `endbr64` no início das funções quase sempre é só um NOP de 4 bytes. Ele só importa para calcular endereços: ao pular o prólogo de uma função, lembre que ele ocupa espaço (veja [Alinhamento da stack](./stack/buffer-overflow/return-address.md#cuidado-ao-sobrescrever-return-address-desalinhamento-de-stack)).
