Tcache (e Tcache Keys)

O tcache (thread cache) foi introduzido na glibc 2.26 como um cache por thread na frente de todas as outras bins. Foi feito para ser rápido, e por isso nasceu praticamente sem verificações: atacar o tcache é mais fácil que atacar as fastbins que ele substituiu. Em qualquer desafio com glibc ≥ 2.26, é o primeiro lugar para olhar.

Funcionamento​

  • Um bin para cada tamanho de chunk de 0x20 a 0x410 (64 bins em x86-64).
  • Cada bin guarda no máximo 7 chunks. O oitavo free do mesmo tamanho segue o caminho antigo (fastbin ou unsorted bin).
  • Lista simplesmente encadeada, LIFO, como a fastbin.
  • O malloc consulta o tcache antes de qualquer outra bin, e o free tenta o tcache antes de qualquer outra bin.

O estado fica na tcache_perthread_struct, alocada na própria heap: é o primeiro chunk (tamanho 0x290 em glibc ≥ 2.30, 0x250 antes).

typedef struct tcache_entry {
  struct tcache_entry *next;          // mesmo lugar do fd
  uintptr_t key;                      // glibc >= 2.29
} tcache_entry;

typedef struct tcache_perthread_struct {
  uint16_t counts[TCACHE_MAX_BINS];           // quantos chunks em cada bin
  tcache_entry *entries[TCACHE_MAX_BINS];     // cabeça de cada bin
} tcache_perthread_struct;

Diferenças em relação à fastbin que importam para exploração:

FastbinTcache
Para onde fd/next apontaHeader do próximo chunkDados do próximo chunk (mem)
Verificação de size ao alocarSimNão
Detecção de double freeSó a cabeça da listaNenhuma (2.26 a 2.28), key (≥ 2.29)
ContadorNãocounts[]: em glibc ≥ 2.30, bin com contador 0 é tratado como vazio

Tcache Poisoning​

Tcache Poisoning é sobrescrever o next de um chunk que está no tcache. O tcache confia no ponteiro: depois que o chunk corrompido sai da lista, a alocação seguinte daquele tamanho devolve o endereço que escrevemos.

char *a = malloc(0x20);
char *b = malloc(0x20);
free(a);
free(b);                     // tcache[0x30]: b → a

*(long *)b = alvo;           // UAF de escrita: tcache[0x30]: b → alvo
                             // (glibc >= 2.32: escreva (b >> 12) ^ alvo)

malloc(0x20);                // devolve b
char *evil = malloc(0x20);   // devolve alvo

Formas de alcançar o next:

  • Use-After-Free de escrita: editar um chunk já liberado. É o caso mais comum.
  • Heap Overflow: transbordar de um chunk alocado para o vizinho que está no tcache.
  • Double Free: o chunk fica alocado e na lista ao mesmo tempo.

Por que liberar dois chunks no exemplo: em glibc ≥ 2.30, o malloc só usa o tcache se counts[idx] > 0. Com um único chunk liberado, o contador vai a zero quando ele sai, e o ponteiro envenenado nunca é usado. Liberar dois (ou mais) deixa o contador em 1 na hora certa.

Requisitos por versão:

glibcO que muda
2.26 a 2.31next em claro, sem verificação. Qualquer endereço serve como alvo
≥ 2.32Safe Linking: escreva (endereço_do_chunk >> 12) ^ alvo, o que exige um leak da heap. O alvo precisa ser múltiplo de 16
≥ 2.34Sem __malloc_hook/__free_hook. Alvos usuais: veja Ataques por versão

Um efeito colateral a lembrar: ao devolver um chunk, o tcache zera o campo key dele (glibc ≥ 2.29), ou seja, grava 8 bytes nulos em alvo + 8.

Libc-Leak com Tcache​

Chunks do tcache só contêm ponteiros para a heap. Para vazar a libc, precisamos de um chunk na unsorted bin, cujo fd/bk apontam para a main_arena (veja Leak de libc pela unsorted bin). Dois caminhos:

1. Encher o tcache. Libere 8 chunks do mesmo tamanho, com chunk maior que 0x80 (acima do limite da fastbin). Os 7 primeiros vão para o tcache e o oitavo vai para a unsorted bin.

char *c[9];
for (int i = 0; i < 9; i++) c[i] = malloc(0x80);   // chunks de 0x90; c[8] é a barreira
for (int i = 0; i < 7; i++) free(c[i]);            // enchem o tcache[0x90]
free(c[7]);                                        // vai para a unsorted bin
printf("%p\n", *(void **)c[7]);                    // UAF de leitura: endereço na libc

2. Chunk grande. Um chunk maior que 0x410 (ex: malloc(0x420)) não cabe no tcache e vai direto para a unsorted bin no primeiro free.

Nos dois casos:

  • O chunk não pode ser vizinho do top chunk, senão é absorvido por ele. Mantenha um chunk alocado depois (a barreira).
  • Aloque tudo antes de começar a liberar. Alocar e liberar um por um só faz o mesmo chunk entrar e sair do tcache.
  • Sem UAF de leitura, dá para alocar de novo por cima do chunk: o malloc não limpa a memória, então os ponteiros antigos continuam lá se o programa não os sobrescrever por inteiro.

Com o leak: libc.address = leak - offset. O offset é constante para cada libc; meça uma vez no GDB (leak - base, com a base do vmmap).

Tcache Keys (glibc 2.29)​

A partir da glibc 2.29, o free grava um valor no segundo campo do chunk (key, em mem + 8) ao colocá-lo no tcache, e o apaga quando o chunk sai.

glibcValor da key
2.29 a 2.33Endereço da tcache_perthread_struct. Ler a key de um chunk livre vaza a heap
≥ 2.34Valor aleatório por processo (tcache_key)

Em cada free, se chunk->key for igual ao valor esperado, a glibc percorre o bin procurando o chunk. Se encontrar, aborta com free(): double free detected in tcache 2.

Contornos

  • Sobrescrever a key: a verificação só é disparada se a key bater. Com um UAF de escrita, altere qualquer byte de mem + 8 e o segundo free passa.
  • Mudar o tamanho: se der para corromper o size do chunk entre os dois free, o segundo vai para outro bin e a busca não o encontra.
  • House of Botcake: libere o chunk uma vez para a unsorted bin (com o tcache cheio) e outra para o tcache (depois de abrir uma vaga). As duas listas não se conhecem.
  • Não usar double free: com UAF de escrita, o Tcache Poisoning direto não depende de nada disso.

Atacando a tcache_perthread_struct​

Como a struct fica na heap, ela mesma é um alvo. Quem consegue escrever nela (por um poisoning apontado para o início da heap, por exemplo) controla counts e entries de todos os bins: cada entries[i] passa a ser um malloc em endereço arbitrário, sem mais nenhuma corrupção. Marcar um contador como 7 também faz o próximo free daquele tamanho ir direto para a unsorted bin.
