Leak de libc pela unsorted bin

Chunks no tcache e nas fastbins só têm o ponteiro fd, que aponta para outro chunk: lê-los vaza no máximo a heap. Para vazar a libc pela heap, o caminho padrão é a unsorted bin: os ponteiros fd e bk de um chunk que está nela apontam para dentro da main_arena, uma variável global da libc.

Receita: (1) fazer um chunk ir para a unsorted bin, (2) ler os primeiros 8 bytes dos dados dele.

Por que o chunk aponta para a libc​

A main_arena é a struct que guarda o estado do alocador, incluindo as cabeças de todas as bins:

struct malloc_state {
    __libc_lock_define (, mutex);
    int flags;
    int have_fastchunks;
    mfastbinptr fastbinsY[NFASTBINS];
    mchunkptr top;                      // top chunk
    mchunkptr last_remainder;
    mchunkptr bins[NBINS * 2 - 2];      // unsorted, small e large bins
    ...
};

Unsorted, small e large bins são listas duplas circulares. Cada uma ocupa dois slots de bins[] (um fd e um bk), e a glibc trata esse par como se fosse um chunk: a "cabeça" da lista. Para a unsorted bin, a cabeça é o par bins[0]/bins[1].

Sendo circular, o último elemento aponta de volta para a cabeça. Com um único chunk na lista, ele é ao mesmo tempo o primeiro e o último:

pwndbg> x/4gx 0x55555555a000
0x55555555a000: 0x0000000000000000      0x0000000000000091     ← prev_size, size
0x55555555a010: 0x00007ffff7dd1b78      0x00007ffff7dd1b78     ← fd, bk: o mesmo endereço da libc

fd == bk com um valor 0x7f... é a assinatura de um chunk sozinho na unsorted bin.

O valor vazado é o endereço da "cabeça" vista como chunk, &main_arena.bins[0] - 0x10, que coincide com &main_arena.top. Em x86-64 isso é main_arena + 96 nas glibc ≥ 2.27 (+ 88 nas anteriores).

libc.address = leak - (libc.sym['main_arena'] + 96)

Se a libc não exporta o símbolo main_arena, meça o offset uma vez no GDB: leak - base_da_libc, com a base tirada do vmmap. Ele é constante para aquela libc. Outra referência: main_arena fica 0x10 bytes depois de __malloc_hook nas glibc que ainda o têm.

Com mais chunks na lista, só o primeiro e o último apontam para a arena (um pelo bk, outro pelo fd); os do meio apontam para vizinhos na heap. Um chunk que já foi movido para uma small ou large bin também aponta para a main_arena, em um offset diferente. Chunks em large bin ainda têm fd_nextsize/bk_nextsize, que apontam para a heap: um único chunk dá os dois leaks.

Levando um chunk até a unsorted bin​

O chunk precisa (a) não caber no tcache nem em fastbin e (b) não ser vizinho do top chunk, senão é absorvido por ele. Mantenha sempre um chunk alocado depois dele, a barreira.

MétodoComoQuando usar
Chunk grandemalloc(0x420) ou mais, e freeO programa permite tamanhos > 0x410
Encher o tcache8 free de chunks entre 0x90 e 0x410: o oitavo vai para a unsorted binTamanho limitado, mas várias alocações (detalhes)
glibc < 2.26Qualquer chunk maior que 0x80Sem tcache
malloc_consolidateFundir chunks das fastbins (abaixo)Só é possível alocar tamanhos de fastbin
Corromper sizeAumentar o size de um chunk pequeno para > 0x410 antes do freeHá overflow, mas só alocações pequenas. O "próximo chunk" calculado pelo novo size precisa parecer válido
char *a = malloc(0x420);
char *barreira = malloc(0x10);
free(a);                              // unsorted bin
printf("%p\n", *(void **)a);          // leak (UAF de leitura)

Lendo os ponteiros​

  • UAF de leitura: imprimir o chunk depois de liberado.
  • Realocar sem limpar: o malloc não zera a memória. Alocar um chunk do mesmo tamanho (ou menor, cortado desse chunk) e imprimir mostra o fd/bk antigos, desde que o programa não os sobrescreva. Se a leitura do programa exige ao menos 1 byte, envie só 1: os 12 bits baixos do endereço são conhecidos e os outros bytes permanecem.
  • Chunks sobrepostos: ler o chunk livre através de outro chunk que o cobre.

malloc_consolidate​

Chunks em fastbin não são fundidos com os vizinhos no free. Isso só acontece quando malloc_consolidate() roda: ela esvazia todas as fastbins, funde cada chunk com os vizinhos livres e coloca o resultado na unsorted bin. É a saída quando o programa só permite alocações pequenas.

Gatilhos:

  • Um pedido de tamanho de large bin (≥ 0x400), mesmo que não venha do nosso malloc direto.
  • O top chunk não ter espaço para o pedido.
  • free de um chunk que, depois de consolidado, passa de 64 KB (FASTBIN_CONSOLIDATION_THRESHOLD).

Quando o programa não deixa pedir tamanhos grandes, use alocações internas da libc:

  • scanf com entrada longa (da ordem de 0x400 caracteres ou mais): o buffer interno cresce na heap.
  • printf com largura enorme (%10000c), em uma format string.
  • stdin/stdout sem setvbuf: o buffer do FILE (0x1000 em pipes/sockets, 0x400 em terminal) é alocado no primeiro uso.

Em glibc ≥ 2.26, os chunks pequenos vão primeiro para o tcache: encha-o (7 por tamanho) para os próximos caírem na fastbin.

Consolidação no free​

Chunks fora do tcache e das fastbins são fundidos com os vizinhos livres no próprio free:

char *a = malloc(0x420);
char *b = malloc(0x420);
char *c = malloc(0x420);
char *barreira = malloc(0x10);

free(a);      // unsorted bin
free(c);      // unsorted bin
free(b);      // funde com a e com c: um único chunk de 0xc90 na unsorted bin

Isso importa por dois motivos. Primeiro, os ponteiros antigos (b, c) passam a apontar para o meio de um chunk livre maior, o que é a base das técnicas de chunks sobrepostos. Segundo, a fusão para trás confia nos campos prev_size e no bit P: forjá-los com um overflow é o que os ataques de Unlink, poison null byte e House of Einherjar exploram.

Resumo​

  1. Tcache/fastbin: leak de heap. Unsorted/small/large bin: leak de libc.
  2. Leve um chunk à unsorted bin (chunk grande, tcache cheio ou malloc_consolidate), com uma barreira antes do top chunk.
  3. Leia fd ou bk e subtraia o offset: libc.address = leak - (main_arena + 96).
  4. Confira: a base tem que terminar em 000.
